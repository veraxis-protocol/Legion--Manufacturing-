2. Tier decision record: each rung and how it was checked

TierResultHow it was checked
1 Vendor MCPNot checkedNo vendor exists to publish one. The system is fictitious and has no product name. This session also has no web search tool, and external contact was out of scope.
2 Community MCPNot checkedSame reasons: no product name to search for, and no search tool in this session. A generic "SQLite MCP" would give schema-wide, possibly writable access, which is broader than the scope asked for.
3 API wrapperRuled outThe target is a database file. It has no API, which the inputs confirm (README lists tables and a view only).
4 Read-only DB accessChosen, testedThe file opened with SQLite mode=ro and PRAGMA query_only=ON. All 3 assets and 3 work orders were read and mapped. The file's SHA-256 was the same before and after the run.
5 ZapierNot neededTier 4 works. A local file has no Zapier trigger in any case.
6 RPANot neededRecommended against by default.
7 Scheduled exportFallback onlyUse this if the real CMMS database cannot be read directly, for example because it is on a server IT will not open up. It needs a nightly CSV of the same two views.

What being one rung lower than Tier 3 gives up: there is no vendor-maintained contract. A schema change in the CMMS will break this connector. The connector checks the schema on every run and stops with SCHEMA DRIFT rather than returning wrong data. Note for the real plant: do not point this at a live production CMMS database. Read a copy, a replica or the two draft views, with the database owner's sign-off.
